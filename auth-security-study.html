1. 인증(Authentication)과 인가(Authorization)

모든 로그인 시스템의 출발점이 되는 두 개념. 이름이 비슷해서 자주 헷갈리지만 완전히 다른 일을 한다.

인증 (Authentication, AuthN)인가 (Authorization, AuthZ)
질문 "너 누구야?" — 신원 확인 "너 이거 해도 돼?" — 권한 확인
예시 아이디/비밀번호 로그인, 지문 인식, OTP 일반 회원은 글 작성 가능, 관리자만 삭제 가능
시점 먼저 일어남 (로그인) 인증 이후 매 요청마다 검사
HTTP 에러 401 Unauthorized (사실상 "인증 안 됨") 403 Forbidden ("누군지는 아는데 권한 없음")
핵심
로그인 = 인증. 로그인 후 "관리자 페이지 접근 가능?"을 따지는 것 = 인가. JWT, 세션, SSO, Keycloak 전부 이 두 가지를 어떻게 구현하느냐에 대한 도구다.

2. 회원가입 보안 — 비밀번호는 절대 그대로 저장하지 않는다

DB가 털렸을 때 피해를 최소화하는 것이 목표. "털리지 않게"가 아니라 "털려도 안전하게"를 설계한다.

2-1. 평문 저장 금지, 해시(Hash) 저장

해시 함수는 단방향이다. 비밀번호에서 해시값을 만드는 것은 쉽지만, 해시값에서 비밀번호를 되돌리는 것은 사실상 불가능하다.

2-2. 단순 해시(SHA-256)로는 부족한 이유

  • 레인보우 테이블 공격: 자주 쓰는 비밀번호의 해시값을 미리 계산해 둔 표. SHA-256("123456")은 전 세계 어디서나 같은 값이므로 표를 만들어 역추적할 수 있다.
  • 속도가 너무 빠름: SHA-256은 초당 수십억 번 계산 가능해 무차별 대입(brute-force)에 취약하다.

2-3. 해결책: Salt + 느린 해시 함수

  • Salt(솔트): 사용자마다 다른 랜덤 값을 비밀번호에 붙여서 해시. 미리 계산해 둔 표가 소용없어진다.
  • 느린 해시 함수:
    • bcrypt — 가장 널리 쓰임. Spring Security의 BCryptPasswordEncoder, Node의 bcrypt 패키지. 솔트가 결과 문자열에 자동 포함된다.
    • Argon2 — 2015년 암호 해싱 대회 우승, 현재 최신 권장. 메모리도 많이 쓰게 해서 GPU 공격까지 방어한다.
    • PBKDF2, scrypt — 역시 사용 가능한 표준 알고리즘.
// Spring Security 예시
PasswordEncoder encoder = new BCryptPasswordEncoder();
String hashed = encoder.encode("mypassword123");   // 저장할 때
encoder.matches("mypassword123", hashed);          // 로그인 검증할 때

// Node.js 예시
const bcrypt = require('bcrypt');
const hashed = await bcrypt.hash(password, 12);    // 12 = cost factor (높을수록 느림=안전)
const ok = await bcrypt.compare(input, hashed);

2-4. 회원가입/로그인 폼에서 추가로 챙길 것

  • HTTPS 필수 — 평문 HTTP로는 비밀번호가 네트워크에서 그대로 노출된다.
  • 로그인 시도 제한 (Rate Limiting) — 5회 실패 시 잠금/캡차 등으로 무차별 대입 방어.
  • 에러 메시지 통일 — "아이디가 없습니다"와 "비밀번호가 틀렸습니다"를 구분해서 알려주면 공격자에게 가입된 아이디 목록을 알려주는 셈이다. "아이디 또는 비밀번호가 올바르지 않습니다"로 통일한다.
  • 비밀번호 정책 — 최소 길이(8자 이상)가 특수문자 강제보다 중요하다. 유출된 비밀번호 목록과 대조하는 것도 좋은 방법.
  • SQL Injection 방어 — 반드시 Prepared Statement / ORM 파라미터 바인딩 사용. 문자열 조립으로 쿼리를 만들지 않는다.
금지
평문 저장, MD5/SHA-1 사용(이미 깨진 알고리즘), 솔트 없이 SHA-256만 사용, 비밀번호를 이메일로 발송(비밀번호 찾기는 재설정 링크로), 비밀번호를 로그에 출력.

3. 로그인 상태 유지 — 세션 방식 vs 토큰 방식

HTTP는 상태가 없다(stateless). 서버는 "방금 로그인한 사람"과 "다음 요청을 보낸 사람"이 같은 사람인지 기본적으로 모른다. 이를 해결하는 두 가지 방식.

3-1. 세션(Session) 방식 — 서버가 기억한다

  • 장점: 서버가 세션을 지우면 즉시 로그아웃/강제 만료가 가능해 통제력이 강하다. 쿠키에는 의미 없는 랜덤 ID만 들어가므로 유출되어도 정보가 없다.
  • 단점: 서버가 상태를 들고 있어야 하므로 서버가 여러 대면 세션 공유 인프라(Redis 등)가 필요하다. 모바일 앱이나 다른 도메인의 API 서버와는 쿠키 기반이 번거로울 수 있다.

3-2. 토큰(Token) 방식 — 클라이언트가 증명서를 들고 다닌다

  • 장점: 서버가 상태를 저장하지 않아(stateless) 서버 확장(scale-out)이 쉽고, MSA에 잘 맞는다. 웹/모바일/타 서비스 어디서든 같은 방식으로 쓸 수 있다.
  • 단점: 발급된 토큰은 만료 전까지 서버가 강제로 무효화하기 어렵다(5장의 Refresh Token 절에서 보완책을 다룬다). 토큰 자체에 정보가 들어 있어 유출 시 위험이 더 크다.
세션토큰(JWT)
상태 저장서버 (stateful)클라이언트 (stateless)
서버 확장세션 공유 인프라 필요쉬움 — 서명 키만 공유
즉시 무효화가능 (세션 삭제)어려움 (만료까지 유효)
어울리는 구조단일 서버 웹 서비스MSA, 모바일 API, 서비스 간 통신

4. JWT (JSON Web Token) 완전 해부

토큰 방식에서 사실상 표준으로 쓰이는 토큰 형식.

4-1. 구조: 점(.)으로 구분된 세 부분

표준 클레임 (Registered Claims)

  • sub (subject) — 사용자 식별자
  • iss (issuer) — 토큰 발급자 (예: https://auth.example.com)
  • aud (audience) — 토큰을 받을 대상 서비스
  • iat (issued at) — 발급 시각
  • exp (expiration) — 만료 시각. 반드시 넣어야 한다.
주의
JWT는 암호화가 아니다. Header와 Payload는 그냥 Base64 인코딩일 뿐이라 누구나 jwt.io에 붙여넣으면 내용을 볼 수 있다. JWT가 보장하는 것은 기밀성이 아니라 무결성(위조 불가)이다. 따라서 Payload에 비밀번호, 주민번호 같은 민감 정보를 절대 넣으면 안 된다.

4-2. 서명이 위조를 막는 원리

4-3. 서명 알고리즘: HS256 vs RS256

HS256 (대칭키)RS256 (비대칭키)
키 하나의 비밀 키로 서명과 검증 모두 개인키로 서명, 공개키로 검증
키 공유 검증하는 모든 서버가 비밀 키를 알아야 함 — 서버가 많을수록 유출 위험 증가 공개키는 유출되어도 됨. 인증 서버만 개인키를 보관
어울리는 곳 단일 서비스 MSA, SSO — Keycloak이 기본으로 사용

RS256 구조에서는 각 마이크로서비스가 인증 서버의 JWKS 엔드포인트(공개키 목록, /.well-known/jwks.json)에서 공개키를 받아와 스스로 토큰을 검증한다. 인증 서버에 매번 물어볼 필요가 없다. (11장 도면 참고)

4-4. JWT 관련 주요 공격과 방어

  • alg: none 공격 — 헤더의 알고리즘을 none으로 바꿔 "서명 없음" 토큰을 보내는 고전 공격. 검증 라이브러리에서 허용 알고리즘을 명시적으로 고정해 방어한다.
  • 알고리즘 혼동 공격 — RS256용 공개키를 HS256의 비밀 키인 척 사용하게 만드는 공격. 역시 알고리즘 고정으로 방어.
  • 약한 비밀 키 — HS256 키가 짧으면 무차별 대입으로 키를 찾아내 마음대로 토큰을 발급할 수 있다. 256비트 이상 랜덤 키를 사용하고, 코드에 하드코딩하지 말고 환경변수/시크릿 관리 도구에 둔다.
  • 만료 미검증 — exp를 검사하지 않으면 유출된 토큰이 영원히 유효하다. 라이브러리 기본 검증을 끄지 말 것.

5. Access Token / Refresh Token 전략

"JWT는 무효화가 어렵다"는 약점과 "만료가 짧으면 자꾸 로그인해야 한다"는 불편함을 동시에 해결하는 표준 패턴.

5-1. 두 토큰의 역할 분담

Access TokenRefresh Token
용도API 요청 시 매번 첨부하는 실제 출입증Access Token이 만료됐을 때 재발급 받는 용도로만 사용
수명짧게 (5~30분)길게 (수일~수주)
노출 빈도모든 요청에 실려 다님 — 유출 가능성 상대적으로 높음재발급 시에만 전송 — 노출 빈도 낮음
서버 저장저장 안 함 (stateless)보통 DB/Redis에 저장 — 서버가 무효화 가능

5-2. 전체 흐름

5-3. 심화: Refresh Token Rotation

재발급할 때마다 Refresh Token도 새것으로 교체하고 이전 것은 폐기하는 기법. 만약 폐기된 (구) Refresh Token이 사용되면 토큰이 탈취되어 두 곳에서 쓰이고 있다는 신호이므로, 해당 사용자의 모든 토큰을 즉시 무효화한다. Keycloak 등 대부분의 인증 서버가 지원한다.

핵심
"자주 쓰는 것은 짧게, 오래 쓰는 것은 서버가 통제 가능하게." — stateless의 장점(Access Token)과 stateful의 통제력(Refresh Token)을 절충한 설계다.

6. 토큰을 어디에 저장할까? — XSS와 CSRF

프론트엔드에서 가장 자주 나오는 논쟁. 두 공격의 경로를 도면으로 이해해야 답을 고를 수 있다.

6-1. XSS — 스크립트가 저장소를 턴다

6-2. CSRF — 쿠키가 자동으로 실려 나간다

6-3. 저장 위치별 비교

저장 위치XSS에CSRF에비고
localStorage / sessionStorage 취약 — JS로 읽을 수 있음 안전 — 자동 전송 안 됨 구현이 간단해서 많이 쓰이지만 XSS 한 번에 토큰이 통째로 털린다
HttpOnly 쿠키 안전 — JS가 읽기 불가 취약 — 자동 전송됨, 별도 방어 필요 SameSite 속성 + CSRF 토큰으로 방어 가능
JS 메모리 (변수) 상대적 안전 — 새로고침하면 사라짐 안전 Access Token은 메모리, Refresh Token은 HttpOnly 쿠키에 두는 조합이 흔한 권장안

6-4. 안전한 쿠키 설정

Set-Cookie: refreshToken=xxx;
    HttpOnly;          // JS에서 접근 불가 — XSS로 못 훔침
    Secure;            // HTTPS에서만 전송
    SameSite=Strict;   // 다른 사이트발 요청에는 안 실림 — CSRF 방어 (또는 Lax)
    Path=/api/token;   // 재발급 엔드포인트에만 전송
    Max-Age=1209600
권장 조합
Access Token은 JS 메모리에만 보관(전역 변수/상태관리), Refresh Token은 HttpOnly + Secure + SameSite 쿠키에. 그리고 근본적으로 XSS 자체를 막는 것이 최우선이다: 출력 이스케이프, 프레임워크의 기본 방어(React의 JSX 등) 신뢰, dangerouslySetInnerHTML 지양, CSP(Content-Security-Policy) 헤더 적용.

7. OAuth 2.0 — 비밀번호를 주지 않고 권한만 위임

"구글로 로그인", "카카오로 로그인" 버튼 뒤에서 일어나는 일. SSO와 Keycloak을 이해하기 위한 필수 배경지식.

7-1. 어떤 문제를 풀려는 것인가

어떤 앱이 "내 구글 캘린더를 읽고 싶다"고 할 때, 내 구글 비밀번호를 그 앱에 알려주는 것은 재앙이다(전체 계정 장악, 회수 불가). OAuth 2.0은 비밀번호 대신, 범위와 기한이 제한된 출입증(Access Token)을 발급해 주는 권한 위임 프레임워크다.

7-2. 등장인물 4명

역할의미"구글 로그인" 예시
Resource Owner자원의 주인 = 사용자나
Client권한을 위임받으려는 앱내가 만든 웹 서비스
Authorization Server인증하고 토큰을 발급하는 서버구글 로그인 서버 (또는 Keycloak)
Resource Server보호된 자원을 가진 API 서버구글 캘린더 API

7-3. Authorization Code Grant — 표준 흐름

여러 흐름(Grant) 중 웹에서 쓰는 표준. 이 순서는 면접에도 자주 나오니 흐름째로 이해해 두자.

왜 코드를 거쳐 두 단계로 나눌까?

  • 4번의 리다이렉트는 브라우저 주소창을 지나므로 노출 위험이 있다. 그래서 노출되어도 되는 일회용 코드만 전달한다.
  • 진짜 토큰은 6~7번에서 서버 간 통신(back channel)으로만 전달되고, client_secret을 아는 진짜 Client만 교환할 수 있다.
  • state 파라미터 — 요청 시 보낸 랜덤값이 그대로 돌아오는지 확인해 CSRF를 방어한다.
  • PKCE — client_secret을 숨길 수 없는 SPA/모바일 앱을 위한 확장. 요청마다 임시 비밀값(code_verifier)을 만들어 코드 탈취 공격을 막는다. 현재는 모든 클라이언트에 권장.

8. OIDC (OpenID Connect) — OAuth 위에 얹은 인증

OAuth 2.0은 원래 인가(권한 위임) 프레임워크인데, 다들 이것을 로그인에 쓰고 싶어 했다. 그래서 표준화된 것이 OIDC.

  • OAuth 2.0 = "이 앱이 내 캘린더에 접근해도 됨" (인가) — 사용자가 누구인지는 표준으로 알려주지 않는다.
  • OIDC = OAuth 2.0 + ID Token — "이 사용자는 누구다"를 표준 방식으로 알려주는 인증 계층.

ID Token의 내용

{
  "iss": "https://keycloak.example.com/realms/myrealm",   // 발급자
  "sub": "f81d4fae-7dec-...",                             // 사용자 고유 ID
  "aud": "my-web-app",                                    // 이 토큰의 대상 클라이언트
  "email": "user@example.com",
  "name": "홍길동",
  "exp": 1725345600,
  "nonce": "요청 시 보낸 랜덤값"                            // 리플레이 공격 방어
}

"구글/카카오로 로그인"은 사실 OIDC(또는 그 유사 구현)이고, Keycloak도 OIDC 표준을 구현한 서버다. OIDC를 지원하는 서버는 /.well-known/openid-configuration 주소에서 모든 엔드포인트 정보를 자동으로 알려준다(Discovery).

9. SSO (Single Sign-On) — 한 번 로그인으로 모든 서비스

구글에 한 번 로그인하면 Gmail, YouTube, Drive에 다시 로그인하지 않아도 되는 것. 그 원리.

9-1. 개념

SSO는 인증을 각 서비스에서 떼어내 중앙의 인증 서버(IdP)에 모으는 구조다.

  • IdP (Identity Provider): 인증을 전담하는 서버. 사용자 계정과 로그인 세션을 여기서만 관리한다. (예: 구글 계정, 회사의 Keycloak)
  • SP (Service Provider): 인증을 IdP에 맡기는 개별 서비스들. (예: Gmail, YouTube / 우리 회사의 서비스 A, B, C)

9-2. 동작 원리 — 핵심은 "IdP의 세션 쿠키"

즉 사용자 입장에서 "한 번만 로그인"으로 보이지만, 실제로는 서비스마다 인증 흐름이 돌고 있고, IdP에서의 로그인 단계만 세션 덕분에 생략되는 것이다.

9-3. SSO 프로토콜 두 계열

OIDC (OpenID Connect)SAML 2.0
기반/형식OAuth 2.0 + JSON/JWTXML
시대모던 웹/모바일 표준2005년~, 기업 환경에 여전히 많음
주 사용처신규 서비스, API, 모바일사내 그룹웨어, 레거시 엔터프라이즈 연동

Keycloak은 둘 다 지원하므로 신규 서비스는 OIDC로, 레거시는 SAML로 하나의 IdP에 붙일 수 있다.

9-4. SSO의 장단점

  • 장점: 사용자 경험 향상. 비밀번호가 IdP 한 곳에만 존재하며 각 서비스는 비밀번호를 아예 저장하지 않는다. 중앙에서 계정 잠금/2단계 인증/정책을 일괄 적용하고, 퇴사자 계정을 한 번에 차단할 수 있다.
  • 단점: IdP가 단일 장애점(SPOF)이다. IdP가 죽으면 전 서비스 로그인 불가, IdP 계정이 털리면 전 서비스가 털린다. 그래서 IdP에는 반드시 MFA(다중 인증)를 건다.
  • Single Logout(SLO) — 로그아웃 전파는 의외로 어려운 문제다. 각 서비스에 이미 발급된 토큰이 남아 있기 때문. OIDC의 Back-Channel Logout 등으로 해결한다.

10. Keycloak — 오픈소스 인증 서버

지금까지 배운 것(비밀번호 해시, JWT, OAuth 2.0, OIDC, SAML, SSO, MFA)을 전부 구현해 놓은 완성품. Red Hat이 주도하는 오픈소스로, 직접 만들면 몇 달 걸릴 인증 서버를 설치만으로 얻는다.

10-1. 내부 구조

10-2. 핵심 개념(용어)

개념설명
Realm (렐름)완전히 격리된 인증 공간. 사용자/클라이언트/설정이 렐름 단위로 분리된다. 보통 서비스(혹은 회사)당 하나. 관리용 master 렐름은 건드리지 말고 새로 만든다.
ClientKeycloak에 인증을 맡기는 앱 하나하나 (React 프론트, Spring 백엔드 등). OAuth의 Client와 같은 의미.
Client Scope토큰에 어떤 클레임을 담을지 정의하는 묶음.
Role인가용 권한. Realm Role(전역)과 Client Role(특정 앱 한정)이 있고, JWT의 클레임으로 들어간다.
Group사용자 묶음. 그룹에 Role을 부여해 일괄 관리.
Identity Provider외부 로그인 중개 설정 (구글, 카카오, 다른 SAML IdP 등).

10-3. 빠르게 띄워보기 (Docker)

docker run -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:latest start-dev

# http://localhost:8080 관리 콘솔 접속 후
# 1) Realm 생성 (예: my-realm)
# 2) Client 생성 (예: my-frontend, redirect URI 등록)
# 3) User 생성 — 이 흐름만으로 OIDC 로그인이 동작한다

OIDC 설정 정보는 여기서 자동 제공된다:

http://localhost:8080/realms/my-realm/.well-known/openid-configuration   # Discovery 문서
http://localhost:8080/realms/my-realm/protocol/openid-connect/certs      # JWKS (공개키)

10-4. 백엔드 연동 예시 (Spring Boot Resource Server)

백엔드는 Keycloak에게 물어볼 필요 없이, 공개키로 JWT를 스스로 검증한다. 설정은 놀랄 만큼 짧다:

# application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8080/realms/my-realm
          # 이 한 줄로 JWKS 공개키를 자동으로 받아와 서명/만료/발급자를 검증한다
// 인가(Role 검사) 예시
http.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ADMIN")   // JWT의 role 클레임 기반
    .anyRequest().authenticated());

프론트엔드(React/Vue)는 keycloak-js 또는 표준 oidc-client-ts 라이브러리로 로그인 리다이렉트와 토큰 갱신을 처리한다.

10-5. 직접 구현 vs Keycloak, 언제 무엇을?

직접 구현 (JWT 발급 코드 작성)Keycloak 도입
학습 목적, 소규모 단일 서비스, 요구사항이 단순할 때. 인증 원리를 이해하려면 한 번은 직접 만들어 보는 것을 강력 추천. 서비스가 여러 개(SSO 필요), 소셜 로그인 + MFA + 계정관리까지 필요, MSA 환경, 기업 LDAP 연동. 인증 코드의 버그는 곧 보안사고이므로 검증된 구현을 쓰는 가치가 크다.

유사한 대안: Auth0, AWS Cognito, Firebase Auth(관리형 서비스), Authentik, Ory(오픈소스). Keycloak은 그중 "직접 호스팅하는 오픈소스" 진영의 사실상 표준이다.

11. MSA 환경에서의 인증 구조

마이크로서비스에서 "누가 검증하느냐"를 정리하면 지금까지의 개념이 하나로 연결된다.

  • 왜 JWT + RS256인가: 서비스가 10개여도 인증 서버에 매 요청 물어보지 않는다. 공개키로 각자 검증하므로 인증 서버 부하가 없고, 서비스 간 결합도가 낮다.
  • 서비스 간 통신 인증: 사용자 없이 서비스끼리 호출할 때는 OAuth의 Client Credentials Grant로 서비스 전용 토큰을 발급받는다.
  • 사용자 컨텍스트 전파: A가 B를 호출할 때 받은 JWT를 그대로 전달하거나(Token Relay), 필요한 클레임만 내부 헤더로 전달한다.
  • 게이트웨이에서 끝내지 말 것: 게이트웨이만 검증하고 내부 서비스는 무방비면, 내부망에 침투한 공격자에게 전부 뚫린다. 각 서비스가 스스로 검증하는 것이 Zero Trust 원칙이다.

12. 실전 보안 체크리스트

로그인/회원가입 기능을 구현하거나 리뷰할 때 하나씩 점검해 보자.

회원가입/비밀번호

  • bcrypt/Argon2로 해시 저장 (평문·MD5·SHA 단독 금지)
  • 모든 구간 HTTPS
  • 로그인 실패 메시지 통일 ("아이디 또는 비밀번호가 올바르지 않습니다")
  • 로그인 시도 제한 / 계정 잠금 / 캡차
  • SQL Injection 방어 (Prepared Statement / ORM)
  • 비밀번호 재설정은 만료되는 일회용 토큰 링크로

JWT/토큰

  • Payload에 민감 정보 넣지 않기 (JWT는 누구나 읽을 수 있다)
  • exp 필수, Access Token 수명 짧게 (5~30분)
  • Refresh Token은 서버 저장 + 무효화 가능 + Rotation
  • 서명 키는 환경변수/시크릿 관리, 충분히 길게. 알고리즘 명시적 고정 (alg: none 방어)
  • MSA/SSO라면 RS256 + JWKS
  • Refresh Token은 HttpOnly + Secure + SameSite 쿠키에

프론트엔드

  • XSS 방어: 출력 이스케이프, CSP 헤더, innerHTML 계열 사용 자제
  • CSRF 방어: SameSite 쿠키 + CSRF 토큰 (쿠키 기반 인증일 때)
  • 토큰을 URL 쿼리스트링에 넣지 않기 (로그와 방문 기록에 남는다)

운영/구조

  • 관리자 계정에 MFA
  • IdP(Keycloak) 이중화 — SSO는 단일 장애점이 된다
  • 비밀번호·토큰을 로그에 남기지 않기
  • 의존성 취약점 점검 (인증 라이브러리 버전 업데이트)
