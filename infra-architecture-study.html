1. 인프라 기초 용어

인프라(Infrastructure)란 애플리케이션 코드가 실제로 실행되는 모든 밑바탕 — 서버, 네트워크, 저장소, 그리고 이들을 관리하는 도구 전체를 말한다.

용어설명
서버요청을 받아 처리하고 응답하는 컴퓨터. 물리 서버(온프레미스) 또는 클라우드의 가상 서버(AWS EC2 등).
IP / 포트IP는 네트워크상의 주소, 포트는 그 주소 안의 문(door). 예: 192.168.0.10:8080. 관례상 HTTP=80, HTTPS=443.
DNS도메인 이름(example.com)을 IP 주소로 바꿔 주는 전화번호부.
웹 서버정적 파일(HTML/CSS/이미지) 제공과 요청 중계 담당. Nginx, Apache. 리버스 프록시로 뒤의 WAS를 감춰 주기도 한다.
WASWeb Application Server. 코드를 실행해 동적인 응답을 만드는 서버. Tomcat(Spring), Node.js, Gunicorn(Python) 등.
DB 서버데이터를 저장/조회. MySQL, PostgreSQL(관계형), Redis(인메모리), MongoDB(문서형) 등.
온프레미스 vs 클라우드직접 서버실을 운영 vs AWS/GCP/Azure에서 빌려 씀. 클라우드는 몇 분 만에 서버를 만들고 지울 수 있어 뒤에 나올 "확장" 이야기의 전제가 된다.
핵심
이 문서 전체를 관통하는 질문은 하나다 — "트래픽과 팀이 커질 때, 구조를 어떻게 바꿔야 하는가?" 모놀리식 → 스케일 아웃 → MSA → 컨테이너 → 쿠버네티스는 전부 이 질문에 대한 단계적 답이다.

2. 모놀리식(Monolithic) 아키텍처

모든 기능이 하나의 프로그램(배포 단위)에 들어 있는 구조. 대부분의 서비스는 여기서 출발하고, 그게 정답인 경우도 많다.

2-1. 장점과 한계

  • 장점: 개발/디버깅/배포/테스트가 전부 단순하다. 트랜잭션 하나로 여러 기능의 데이터 일관성을 보장할 수 있다. 소규모 팀과 초기 서비스에 최적.
  • 한계 1 — 부분 확장 불가: 주문 기능만 트래픽이 몰려도 전체 애플리케이션을 통째로 복제해야 한다.
  • 한계 2 — 배포 리스크 집중: 결제 모듈 한 줄 수정에도 전체를 다시 배포하고, 버그 하나가 서비스 전체를 죽일 수 있다.
  • 한계 3 — 기술/팀 결합: 전체가 하나의 언어/프레임워크에 묶이고, 코드가 커질수록 여러 팀이 한 코드베이스에서 충돌한다.
핵심
모놀리식은 "낡은 방식"이 아니라 출발점이다. 문제가 실제로 생기기 전까지는 가장 생산적인 구조이며, MSA로 가기 전 중간 단계로 모듈 경계만 엄격히 나눈 모듈러 모놀리스를 거치는 것이 정석으로 통한다.

3. 확장 — 스케일링, 로드밸런서, 캐시

사용자가 늘어나 서버 한 대가 버티지 못할 때. 구조를 바꾸기 전에 먼저 쓰는 무기들.

3-1. 스케일 업 vs 스케일 아웃

  • 스케일 아웃의 전제 조건: 서버가 상태를 갖지 않아야(stateless) 한다. 세션 같은 상태는 Redis 등 공유 저장소로 빼야 어느 서버로 요청이 가도 동일하게 처리된다. (인증 문서에서 본 세션 공유 문제와 같은 이야기)
  • 로드밸런서(LB): 요청을 여러 서버에 분배. 라운드 로빈/최소 연결 등 알고리즘, 헬스 체크로 죽은 서버 자동 제외. Nginx, HAProxy, AWS ELB.

3-2. 전형적인 3계층(3-tier) 구성

  • 캐시: DB보다 수십 배 빠른 메모리에 자주 읽는 데이터를 복사해 둠. 만료 시간(TTL)과 갱신 전략(Cache-Aside가 기본)이 핵심 설계 포인트.
  • CDN: 이미지/JS 같은 정적 파일을 전 세계 엣지 서버에 캐싱해 사용자와 가까운 곳에서 제공. 원본 서버 부하도 줄어든다.
  • DB 확장: 읽기 복제본(Read Replica)으로 조회 분산, 더 커지면 샤딩(데이터 수평 분할). DB는 상태 그 자체라 확장이 가장 어렵다 — 그래서 캐시로 먼저 버틴다.

4. MSA (마이크로서비스 아키텍처)

스케일 아웃으로도 해결되지 않는 문제 — "팀과 코드가 너무 커졌다" — 를 푸는 구조. 애플리케이션 자체를 기능 단위의 독립 서비스로 쪼갠다.

4-4. MSA의 대가 (트레이드오프)

  • 분산 시스템의 복잡성: 메서드 호출이 네트워크 호출로 바뀐다 — 느려지고, 실패할 수 있고, 추적이 어렵다. 타임아웃/재시도/서킷 브레이커(장애 전파 차단) 설계가 필수가 된다.
  • 데이터 일관성: DB가 나뉘어 하나의 트랜잭션으로 묶을 수 없다. 사가(Saga) 패턴 — 실패 시 보상 트랜잭션으로 되돌리기 — 같은 복잡한 기법이 필요하다.
  • 운영 부담 폭증: 배포 대상이 1개에서 수십 개가 된다. 이 부담을 감당하게 해 주는 것이 바로 다음 장의 컨테이너와 쿠버네티스다.
주의
MSA는 기술 문제 이전에 조직 문제다. 서비스 경계는 팀 경계와 비즈니스 도메인(DDD의 Bounded Context)을 따라 그어야 하며, 작은 팀이 처음부터 MSA로 시작하는 것은 대부분 과잉 설계다.

5. VM, 컨테이너, Docker

"내 컴퓨터에서는 되는데요?"를 없애는 기술. 수십 개의 마이크로서비스를 현실적으로 굴리기 위한 포장 단위.

5-1. 가상머신(VM) vs 컨테이너

VM컨테이너
격리 단위OS 전체 (게스트 OS 포함)프로세스 (커널은 호스트와 공유)
크기 / 시작 속도수 GB / 분 단위수십 MB / 초 단위
격리 강도강함 (하드웨어 수준)상대적으로 약함 (프로세스 수준)
어울리는 곳서로 다른 OS, 강한 격리 필요MSA, 배포 표준화, 밀도 높은 운영

5-2. Docker의 작업 흐름

# Dockerfile 예시 (Spring Boot)
FROM eclipse-temurin:21-jre          # 베이스 이미지
COPY build/libs/app.jar /app.jar     # 빌드 결과물 복사
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app.jar"]

# 빌드하고 실행
docker build -t myapp:1.0 .
docker run -d -p 8080:8080 myapp:1.0
핵심
이미지는 불변(immutable)이다. 서버에 들어가 고치는 것이 아니라, 새 이미지를 만들어 통째로 교체한다. 이 "불변 인프라" 개념이 뒤의 쿠버네티스와 GitOps 전체를 떠받친다.

6. Kubernetes(K8s) 구조

컨테이너가 수십~수천 개가 되면 사람 손으로는 못 굴린다. "어느 서버에 띄울지, 죽으면 어떻게 할지, 트래픽은 어떻게 나눌지"를 자동화하는 컨테이너 오케스트레이터. K8s라는 이름은 K와 s 사이 8글자(ubernete)를 줄인 표기다.

6-1. 선언형(Declarative) — 쿠버네티스 이해의 열쇠

쿠버네티스에는 "서버 3번에 컨테이너를 띄워라" 같은 명령을 내리지 않는다. 대신 "이 앱은 항상 3개가 떠 있어야 한다"라는 원하는 상태(desired state)를 선언하면, 쿠버네티스가 실제 상태를 끊임없이 비교하며 알아서 맞춘다. 컨테이너가 죽으면 스스로 다시 띄우는 자가 치유(self-healing)도 이 원리의 결과일 뿐이다.

6-2. 클러스터 구조 — 컨트롤 플레인과 워커 노드

구성 요소역할
API 서버모든 명령과 통신이 지나는 유일한 관문. kubectl도, 내부 부품끼리도 전부 API 서버를 통해 대화한다.
etcd클러스터의 모든 상태(무엇이 어디에 떠 있어야 하는가)를 저장하는 분산 키-값 저장소. 클러스터의 "진실의 원천".
스케줄러새 Pod을 CPU/메모리 여유, 제약 조건을 따져 어느 노드에 둘지 결정.
컨트롤러 매니저"선언 상태 = 실제 상태"가 되도록 감시하고 조치하는 제어 루프들의 모음.
kubelet각 노드의 관리인. 지시받은 Pod을 컨테이너 런타임으로 실행하고 상태를 보고.
kube-proxy각 노드의 네트워크 담당. Service로 들어온 트래픽을 실제 Pod으로 전달.
컨테이너 런타임실제로 컨테이너를 실행하는 엔진. containerd, CRI-O.

7. K8s 핵심 오브젝트

쿠버네티스에 "선언"하는 대상들. YAML로 작성해 kubectl apply로 제출한다.

오브젝트역할
Pod배포의 최소 단위. 컨테이너 1개 이상을 담는 상자(보통 1개). IP를 갖지만 언제든 죽고 다시 태어나는 소모품.
ReplicaSet"Pod N개 유지"를 책임. 죽으면 새로 만든다.
DeploymentReplicaSet의 상위 개념. 무중단 롤링 업데이트와 롤백을 관리. 실무에서 앱 배포는 대부분 이것.
Service수시로 바뀌는 Pod들 앞의 고정된 접점(가상 IP + 내부 DNS 이름). 자동 로드밸런싱. MSA의 서비스 디스커버리를 여기서 해결.
Ingress클러스터 외부의 HTTP(S) 트래픽을 도메인/경로 규칙에 따라 Service로 라우팅. TLS 종료도 담당.
ConfigMap / Secret설정값 / 민감정보(비밀번호, 인증서)를 코드와 분리해 주입.
Namespace클러스터 안의 논리적 칸막이 (dev / staging / prod 분리 등).
PV / PVCPod이 죽어도 남아야 하는 데이터를 위한 영구 저장소.
HPAHorizontal Pod Autoscaler. CPU 사용률 등에 따라 Pod 수를 자동 증감 — 스케일 아웃의 자동화.

7-2. 자가 치유(Self-Healing)의 동작

# Deployment + Service 선언 예시
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3                      # 항상 3개 유지 (자가 치유의 기준)
  selector:
    matchLabels: { app: order }
  template:
    metadata:
      labels: { app: order }
    spec:
      containers:
      - name: order
        image: myregistry/order:1.2.0   # 불변 이미지
        ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata:
  name: order-service              # 클러스터 내부 DNS 이름이 됨
spec:
  selector: { app: order }         # 이 라벨의 Pod들에게 분배
  ports: [{ port: 80, targetPort: 8080 }]

8. K8s vs K3s vs K9s — 이름은 비슷해도 전혀 다르다

셋 중 둘은 "쿠버네티스"고, 하나는 쿠버네티스를 "보는 도구"다. 면접에서도 헷갈리기 쉬운 부분.

K8sK3sK9s
정체컨테이너 오케스트레이터 표준K8s의 경량 배포판 (Rancher/SUSE 제작, CNCF 프로젝트)클러스터 관리용 터미널 UI 도구
실행 위치서버 (클러스터 구성)서버 (클러스터 구성)내 컴퓨터 (클라이언트)
특징완전한 기능, 높은 운영 복잡도etcd 대신 SQLite 기본, 불필요 기능 제거, 설치 한 줄kubectl 명령을 화면 탐색으로 대체, 실시간 로그/리소스 뷰
쓰는 상황프로덕션 대규모 운영라즈베리파이, 엣지, CI, 로컬 학습K8s/K3s를 운영·디버깅할 때 항상

8-1. 함께 알아두면 좋은 것들

이름정체
minikube / kind내 컴퓨터에 1노드 학습용 클러스터를 띄우는 도구 (kind는 Docker 컨테이너를 노드처럼 사용).
EKS / GKE / AKSAWS / Google / Azure의 관리형 쿠버네티스 — 컨트롤 플레인 운영을 클라우드가 대신해 준다. 실무 표준.
Helm쿠버네티스의 패키지 매니저. 수십 개 YAML을 "차트" 하나로 묶어 설치/버전 관리.
Rancher여러 클러스터를 웹 UI로 통합 관리하는 플랫폼 (K3s를 만든 회사의 제품).
추천 학습 경로
Docker로 컨테이너 개념 익히기 → 로컬에 K3s(또는 minikube) 설치 → Deployment/Service/Ingress 직접 배포 → K9s로 클러스터 관찰 → 관리형(EKS 등)으로 확장. K3s는 가벼워서 학습용으로 특히 좋다.

9. 배포 전략 — 무중단으로 새 버전 내보내기

서비스를 멈추지 않고 v1을 v2로 바꾸는 세 가지 표준 방법. 쿠버네티스 Deployment의 기본은 롤링 업데이트다.

  • 롤링: K8s 기본값. maxSurge(초과 허용), maxUnavailable(중단 허용)로 속도 조절.
  • 블루-그린: 전환은 Service의 라벨 셀렉터를 바꾸는 것만으로 가능. DB 스키마 호환성이 함정 포인트.
  • 카나리: 정교한 비율 제어는 Ingress 가중치나 서비스 메시(Istio)로. Argo Rollouts 같은 도구가 자동화해 준다.
  • 모든 전략의 공통 전제: 헬스 체크(readiness/liveness probe) — 준비 안 된 Pod에 트래픽을 주지 않고, 죽은 Pod을 감지한다.

10. 요청의 전체 여정 (종합)

지금까지의 조각을 전부 이어 붙이면, 사용자가 주소창에 엔터를 친 순간부터 이런 일이 벌어진다.

11. CI/CD, IaC, GitOps — 인프라를 코드로 움직이기

사람이 서버에 접속해서 배포하는 시대는 끝났다. 코드 푸시부터 운영 반영까지 전 과정을 자동화한다.

11-1. 용어 정리

개념의미대표 도구
CI (지속적 통합)푸시할 때마다 자동으로 빌드+테스트해 문제를 즉시 발견GitHub Actions, Jenkins, GitLab CI
CD (지속적 배포)검증된 결과물을 자동으로 운영 환경까지 반영ArgoCD, Argo Rollouts, Spinnaker
IaC (Infrastructure as Code)서버/네트워크 구성 자체를 코드로 선언 — 리뷰, 이력, 재현 가능Terraform, Ansible
GitOps"Git 저장소 = 운영 상태의 유일한 진실". Git이 바뀌면 클러스터가 따라온다ArgoCD, Flux

11-2. 전체 파이프라인

  • 배포 이력 = Git 커밋 이력. 롤백 = git revert 한 번.
  • 누군가 클러스터를 수동으로 고치면 Git과 어긋난 상태(drift)를 ArgoCD가 감지하고 되돌린다 — 운영 상태가 항상 코드와 일치.
  • Terraform은 그 아래층(클러스터 자체, VPC, DB 인스턴스 생성)을 같은 원리로 코드화한다.

12. 관측성(Observability)과 서비스 메시

수십 개 서비스가 수백 개 Pod으로 흩어지면 "지금 어디가 아픈가"를 보는 능력이 곧 운영 능력이다.

12-1. 관측성의 3대 축

축답하는 질문대표 스택
메트릭 (Metrics)"수치가 어떤가?" — CPU, 응답시간, 에러율Prometheus(수집) + Grafana(대시보드)
로그 (Logs)"무슨 일이 있었나?" — 이벤트 기록ELK(Elasticsearch+Logstash+Kibana), Loki
트레이싱 (Tracing)"이 요청이 어느 서비스에서 느려졌나?" — 호출 경로 추적Jaeger, Zipkin, OpenTelemetry(표준)
  • 알림(Alerting): 지표가 임계치를 넘으면 자동 호출 — Alertmanager, PagerDuty.
  • MSA에서는 요청 하나가 서비스 5~6개를 지나므로, 요청마다 추적 ID를 붙여 전 구간을 잇는 분산 트레이싱이 특히 중요하다.

12-2. 서비스 메시 (Service Mesh) — 짧게

서비스 간 통신의 공통 관심사(암호화 mTLS, 재시도, 타임아웃, 트래픽 비율 제어, 통신 지표 수집)를 애플리케이션 코드에서 떼어내, 각 Pod 옆에 붙는 사이드카 프록시가 대신 처리하게 하는 계층. 대표 구현은 Istio, Linkerd. 강력하지만 복잡도가 높아 "충분히 커진 뒤에 도입"이 정석이다.

13-1. 인프라 진화의 전체 흐름

13-2. 단계별 점검 체크리스트

서버 한 대 시절

  • 배포 절차가 문서화/자동화되어 있는가 (최소한 스크립트)
  • DB 백업이 자동으로 돌고, 복구를 실제로 해봤는가
  • 도메인 + HTTPS + 방화벽(필요한 포트만 개방) 기본기

확장 시점

  • 애플리케이션이 stateless한가 (세션을 Redis 등으로 분리했는가)
  • LB 헬스 체크 경로가 있는가 (/health)
  • 읽기 트래픽을 캐시/리드 레플리카로 분산했는가

MSA 전환 시점

  • 서비스 경계가 팀/도메인 경계와 일치하는가
  • 서비스별 DB 분리 원칙을 지켰는가
  • 타임아웃/재시도/서킷 브레이커가 모든 원격 호출에 있는가
  • 분산 트레이싱 없이 장애 원인을 찾을 수 있는가 (없다면 도입)

쿠버네티스 운영

  • 모든 Pod에 리소스 요청/제한(requests/limits)과 프로브 설정
  • 수동 kubectl 수정 금지 — 모든 변경은 Git을 통해서 (GitOps)
  • Namespace로 환경 분리, Secret은 암호화 관리
  • 모니터링/알림이 배포보다 먼저 준비되어 있는가
